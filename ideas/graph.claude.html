TokenMonitor — 想法图

TokenMonitor 是一个本地优先的跨平台托盘应用（Tauri v2 + Svelte 5），把 Claude Code、 Codex CLI 和 Cursor 三家 AI 编码工具散落在磁盘上的 JSONL 会话日志读出来、定价、聚合， 然后在托盘弹窗和悬浮球里显示"花了多少钱"和"额度用了百分之多少"。它不代理任何请求、 不上传任何数据，除了拉取公共定价表和三家官方的额度接口之外完全离线。 三条主线：把数字算准（解析 + 定价 + 缓存）、把历史留住（归档 + 导入导出 + 远端同步）、 把它装到别人机器上（单实例 + 自动更新 + 最小权限面）。

把应用会读的每个磁盘位置登记在同一个模块里 已完成I-001

是什么
把应用会读的每一个文件系统位置（Claude 项目目录、Codex 会话目录、Cursor 的 state.vscdb、~/.ssh/config、~/.claude/settings.json、凭据文件）都登记在一个 模块里，并让它能被枚举出来给用户看。
为什么有这个想法
这是一个"读你本地日志"的应用，用户凭什么信它？如果访问路径散落在十几个解析器里， 既没人能回答"它到底读了什么"，隐私披露面板也只能靠人肉维护、迟早说谎。
预期结果
`accessed_paths()` 返回的列表与设置里"隐私"面板显示的一致；新增一个 provider 时， 忘记登记路径会在测试里暴露，而不是在用户投诉里暴露。
如何实现
`paths.rs` 用 `AccessedPath { path, purpose, .. }` 结构统一描述每个位置， 各 provider 的默认根目录都由这里的函数产出，`accessed_paths()` 汇总成一份可展示的清单。
为什么这样实现
AGENTS.md 把它写成硬约定："Every filesystem location the app reads must be registered in src-tauri/src/paths.rs"。集中登记是为了让隐私声明可以从代码生成，而不是靠文档追赶代码。

三家的日志格式归一成同一种用量条目 已完成I-003

是什么
三家 provider 的原始日志格式完全不同，全部归一到同一个 `ParsedEntry` （时间戳、模型键、原始模型名、输入/输出/两档缓存 token、web search 次数、 provider、来源、作用域），再由它聚合成 `UsagePayload` 给前端。
为什么有这个想法
如果不归一，定价、聚合、归档、导出、图表每一层都要认三种格式， 任何一层漏掉一种就是静默少算钱。
预期结果
定价、归档、导出、设备聚合都只认 `ParsedEntry` / `ArchivedHourly`； 新 provider 只要能产出 `ParsedEntry` 就自动获得后面所有能力。
如何实现
`usage/parser.rs` 定义 `ParsedEntry`，`models.rs` 定义面向前端的 `UsagePayload` / `ChartBucket` / `ModelSummary` 等 IPC 结构， 前端 `src/lib/types/` 镜像同一批类型。
为什么这样实现
作者本人的说法：统一，方便，之后好兼容。也就是说这个字段集不是为了精确描述任何一家 provider 的日志，而是取三家的并集加上下游（定价/归档/导出/图表）需要的东西—— 宁可让某些 provider 的某些字段恒为 0，也不让下游认三种格式。 代价是接第四家时字段集可能还要再扩一次，收益是扩的时候只改这一处。

会随外部世界变化的常量集中放进一份 JSON 已完成I-004

是什么
所有会随外部世界变化的常量——各家 API base、定价表 URL、汇率 URL、缓存 TTL、 Claude 各套餐的月费——放进 `ops.json`，编译期 include 进二进制， 同一份也给前端读。
为什么有这个想法
套餐涨价、接口换域名、TTL 需要调，这些都不该是"改代码 + 发版"级别的事， 也不该在前后端各写一份然后对不上。
预期结果
`ops()` 能读出套餐预算和全部 URL；前端的 plan tier 成本与后端同源（有测试锁定）。
如何实现
`ops.rs` 用 `include_str!("ops.json")` + `OnceLock` 解析一次； 前端 `providerMetadata.ts` 直接 import 同一个 JSON 取 `plan_tier_costs_usd`。 注意：这是**纯编译期** include，没有任何运行时覆盖路径（无 env、无 app_data_dir 同名文件、 无远端拉取、tauri.conf.json 的 bundle 块也没有 resources），改了必须重新编译发版。
为什么这样实现
文档层面的理由写在 `ops.json:2` 的 `_notes` 和 `ops.rs:38`（"`plan_tier_costs_usd` is deliberately absent here: the frontend imports it"）——集中一处、前后端同源。 「为什么不做成运行时可覆盖」这条**代码里没有写明**，但有一个很硬的现实约束： `ops.json` 的 `urls` 里有 5 条会被贴上凭据的 origin——`anthropic_usage` / `anthropic_account` 走 `bearer_auth(token)`（`rate_limits/claude.rs:331-341`）， 三条 cursor origin 分别走 `basic_auth(api_key)` / `Cookie: WorkosCursorSessionToken` / `bearer_auth`（`cursor_parser.rs:733-744`、`rate_limits/cursor.rs:245-252`）。 让用户目录下一个可写 JSON 决定这些地址，等于给本地任意进程一个把 OAuth token 转发到任意主机的开关；而引入 ops.json 的那次提交标题正是 `fix(usage): stop undercounting spend and leaking the Cursor API key`。 （这段安全推理是本次扫描的分析，不是代码或提交信息里的原话。）
